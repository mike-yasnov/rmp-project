В этом проекте команда отвечает не только за набор сервисов, а за связность общей модели: требования, архитектуру, реализацию, измеримость и честное описание ограничений.

Что сделано

Учебная брокерская система с полным контуром данных

Источник данных

Linux kernel module создаёт /dev/quotes; Go ingestion читает устройство или включает fallback-генератор.

Хранилища

ClickHouse хранит котировки и свечи. PostgreSQL хранит пользователей, счета, сделки и портфель.

Backend

API Gateway отдаёт REST/WebSocket API. Core Banking выполняет операции BUY/SELL в транзакции PostgreSQL.

Клиенты и проверка

Есть Kotlin/Compose и React Native клиенты, load-tester, Jaeger, Prometheus и Grafana.

Что показываем на защите

Не список библиотек, а работающие сценарии и проверяемые свойства

  • GET /api/quotes и GET /api/quotes/{ticker}/candles читают данные из ClickHouse.
  • POST /api/trades меняет баланс, портфель и журнал сделок атомарно.
  • WS /ws/quotes получает события из Redis Pub/Sub.
  • Jaeger показывает путь запроса, Grafana показывает метрики backend.
Котировки можно временно потерять в WebSocket, но история остаётся в ClickHouse.
Финансовую операцию нельзя применить частично: PostgreSQL transaction + row locks.
Нагрузка задаётся параметрами load-tester, а не словами «держит много».
Слабые места названы отдельно, без попытки выдать MVP за production-финтех.

Хранит таблицу quotes; из неё строятся последние цены и OHLCV-свечи.

Redis

Компромисс

Финансовый контур

Core Banking: что происходит при сделке

  • Вход: userId, ticker, action, lots, pricePerLot.
  • SELECT ... FOR UPDATE блокирует счёт пользователя на время операции.
  • BUY проверяет баланс; SELL проверяет доступные лоты.
  • После проверки обновляются accounts, portfolio, trades и выполняется COMMIT.

Нагрузка

Как устроен load-tester

Профиль

Боты создают пользователей, читают котировки, выполняют BUY/SELL и держат WebSocket.

Параметры

BOT_COUNT, ACTIVE_REQUESTS, WS_PERCENT, DURATION_SEC, задержки между запросами.

Метрики

RPS, error rate, avg/p95/p99 latency, число WebSocket-сессий, состояние БД и сервисов.

Главная метрика не «запустилось», а latency и error rate при заданном профиле нагрузки.

Честная самокритика

Где архитектура упрощена и что надо усиливать

  • Double для денег — учебное упрощение; нужен decimal domain.
  • Цена сделки приходит от клиента; нужен серверный price snapshot.
  • Redis Pub/Sub — at-most-once, не подходит для финансовых событий.
  • WebSocket broadcast требует backpressure и очередей на сессию.
  • DTO дублируются между backend и мобильными клиентами.
  • Нужны OpenAPI-контракт и contract tests.
  • Load testing должен фиксировать p95/p99, а не только среднее.
  • Observability требует SLO, alert rules и trace-id в логах.

Итог

Что готово к демонстрации

Стенд поднимается через Docker Compose, клиенты работают с единым API, котировки идут через ClickHouse/Redis/WebSocket, сделки фиксируются в PostgreSQL, а поведение системы видно в Jaeger и Grafana.
